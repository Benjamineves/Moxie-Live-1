System Architecture

The core architectural fact: one vessel profile URL, four conditional render states gated by authenticated role. Everything else follows from this.

URL structure

-- Public (no auth, default)
moxie.sh/MXE-00001

-- Scan entry point (pre-auth animation, then redirects)
moxie.sh/MXE-00001?scan=1

-- Owner (authenticated, session cookie or JWT)
moxie.sh/MXE-00001?role=owner

-- Marina operator (authenticated via marina account)
moxie.sh/MXE-00001?role=marina&mid=portobello-01

-- Coast Guard (authenticated via CG credentials)
moxie.sh/MXE-00001?role=coastguard

Rendering logic (pseudocode)

function renderVesselProfile(mxeId, session) {
  const vessel = db.vessels.find(mxeId)
  const role   = session?.role ?? 'public'

  // Same data, filtered by role tier
  return {
    public:     filterFields(vessel, ROLE_PUBLIC),
    owner:      filterFields(vessel, ROLE_OWNER),     // requires vessel.ownerId === session.userId
    marina:     filterFields(vessel, ROLE_MARINA),    // requires marina auth
    coastguard: filterFields(vessel, ROLE_CG),        // requires CG auth
  }[role]
}

Recommended stack

Stack is flexible — use whatever you're comfortable with. Constraints that matter: short memorable URLs (moxie.sh/MXE-XXXXX), file storage for document uploads (S3 or equivalent), role-based JWT or session auth, and a QR code generator that can encode the scan URL. A simple Node/Express + PostgreSQL + S3 stack covers everything. A serverless approach (Vercel + Supabase + S3) would also work well and deploys fast.

Note on moxie.sh vs moxieyachting.com: The short domain moxie.sh is ideal for QR codes — fewer characters = denser QR = better scan reliability. The marketing site lives at moxieyachting.com. Both can run on the same backend.

Data Model — User

users {
  id            uuid         PRIMARY KEY
  email         text         UNIQUE NOT NULL
  phone         text
  full_name     text
  role          enum         ('owner','marina_operator','coastguard','admin')
  marina_id     uuid         REFERENCES marinas(id)   -- if marina_operator
  created_at    timestamp
  last_login    timestamp
}
One owner, multiple vessels: The relationship is one-to-many. A user owns N vessels. Each vessel has one owner_id foreign key. The "My Fleet" UI queries vessels WHERE owner_id = session.userId.

Data Model — Documents

vessel_documents {
  id            uuid       PRIMARY KEY
  vessel_id     uuid       REFERENCES vessels(id)
  doc_type      enum       ('registration','insurance','boater_card','charter','service','other')
  file_name     text
  file_size     integer    -- bytes
  mime_type     text
  s3_key        text       -- S3 object key (never exposed directly to client)
  expiry_date   date       -- drives the green/amber/red status dots
  visibility    enum       DEFAULT 'owner' ('owner' | 'marina' | 'coastguard')
  uploaded_at   timestamp
}
Document access: Never serve S3 file URLs directly. Generate signed URLs server-side with short TTLs (15 min). The client never sees the S3 key.

QR Routing Logic

Every QR sticker encodes a single URL: https://moxie.sh/MXE-00001. The server handles role detection and the scan animation as follows:

-- Request flow on QR scan:

1. Phone camera scans QR
2. Browser navigates to moxie.sh/MXE-00001

3. Server checks session:
   - No session or unknown role → serve scan_success.html with vessel preview data
                                   → after 2.4s, redirect to profile with role=public
   - Valid owner session         → redirect immediately to profile with role=owner
   - Valid marina session        → redirect immediately to profile with role=marina
   - Valid CG session            → redirect immediately to profile with role=coastguard

4. Profile page receives role param → renders appropriate tier

-- The scan animation receives minimal vessel data for the name flash:
GET /api/vessels/MXE-00001/preview
→ { vessel_name, make, model, year, type }  -- public fields only, no auth required

Open Questions

Items that need a decision before or during P1 build. Most don't block P0.

QuestionContextBlocks
Coast Guard auth method How does a CG officer authenticate? Options: (a) a per-vessel one-time access code generated on demand, (b) standing CG accounts provisioned by Moxie, (c) no auth but a "request access" flow that notifies the owner. Option (a) is simplest for v1. P2-B
Marina operator provisioning How does a marina get an account? Moxie admin creates it manually for v1 (Emery Cove pilot). Self-serve marina signup is a later feature. P1-A
Short domain (moxie.sh) Has this domain been acquired? QR codes benefit significantly from shorter URLs. moxieyachting.com works but produces denser QR grids. P1-B
MXE ID format Current design uses MXE-00001 through MXE-99999 (5 digits). Should this be longer to avoid guessable sequential IDs? Consider MXE-[random 6 char] instead of sequential. P0-A
Boat photo upload The vessel hero currently shows a decorative navy/gold background. Owner can upload a real boat photo. Where in the flow does this happen — during intake (Step 1) or as an edit after registration? P0-D
Document expiry notifications The red/amber/green status dots are powered by expiry_date fields. Should Moxie send email reminders when insurance or registration is approaching expiry? Simple scheduled job, high value for owners. P2-A
Multi-owner vessels Not in scope for v1. Ben owns both vessels outright. But charter vessels (Polaris) have complex ownership. Defer. Future
Ready to build: P0-A (static public profile, hardcoded data) can be deployed in a single afternoon — just serve moxie_vessel_profile_all_roles.html at a real URL with the public render active. That gives Ben a live, scannable profile link to share immediately while the full backend is built.
